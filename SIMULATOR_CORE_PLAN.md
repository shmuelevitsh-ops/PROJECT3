## Stage 2 — CLI parsing and validation (no execution)

**New files:** `Simulator/include/Simulator/CliOptions.h`, `Simulator/src/CliOptions.cpp`.

**Shape:**
```cpp
namespace simulator {

struct ComparativeOptions {
    std::filesystem::path simulation_composition_file;
    std::filesystem::path mission_control_folder;
    std::filesystem::path algorithm_so_file;
    std::vector<std::filesystem::path> mission_control_libraries; // *.so directly under mission_control_folder, non-empty
    std::optional<int> num_threads;
    bool verbose = false;
};

struct CompetitionOptions {
    std::filesystem::path simulation_composition_file;
    std::filesystem::path mission_control_so_file;
    std::filesystem::path algorithms_folder;
    std::vector<std::filesystem::path> algorithm_libraries; // *.so directly under algorithms_folder, non-empty
    std::optional<int> num_threads;
    bool verbose = false;
};

// On any validation failure: prints "Usage: ..." plus a specific message to
// std::cerr, returns std::nullopt. Caller's only remaining job is `return 1;`.
[[nodiscard]] std::optional<std::variant<ComparativeOptions, CompetitionOptions>>
parseCliOptions(int argc, char** argv);

} // namespace simulator
```

**Required argument grammar** (from the assignment; implement exactly):
- Mode selection: scan the *entire* argument list (`argv[1..argc-1]`) for exactly one occurrence of the literal token `-comparative` or `-competition` — do not assume it is `argv[1]`. The assignment's "All command line arguments can appear in any order" is unqualified; nothing carves out an exception for the mode flag, and the example invocations (mode shown first) are illustrative, not a fixed-order requirement. Scanning the whole list is a strict superset of accepting mode-first input, so it is safe regardless of how the grader actually invokes the program. Neither token present, or both present, is a usage error. Every other argument, at any position (including before the mode token), is parsed as `key=value` or the bare `-verbose` flag.
- Remaining args are `key=value`, any order, no spaces around `=`.
- Comparative requires: `simulation=`, `mission_control_folder=`, `algorithm=`. Competition requires: `simulation=`, `mission_control=`, `algorithms_folder=`. Both accept optional `num_threads=` and the optional bare flag `-verbose` (no `=`).
- `simulation=` / `algorithm=` / `mission_control=` must name an existing, openable file — else usage + error, `return std::nullopt`.
- `mission_control_folder=` / `algorithms_folder=` must be an existing, traversable directory containing at least one entry whose extension is exactly `.so` — else usage + error. Populate `mission_control_libraries` / `algorithm_libraries` with every such `.so` path found directly in that folder (non-recursive; skip subdirectories and non-`.so` entries — this naturally skips an earlier run's own `comparative_results_*`/`competition_*` output directory if it happens to sit inside the same folder).
- "Unsupported" is evaluated against the *active mode's* own key set, not the union of both modes': under `-competition`, `mission_control_folder=`/`algorithm=` (comparative-only keys) are unsupported, and symmetrically `mission_control=`/`algorithms_folder=` are unsupported under `-comparative`. Unsupported `key=value` args present → usage + list every unsupported key, `return std::nullopt`. Missing mandatory args (for the active mode) → usage + list every missing key, `return std::nullopt`.
- A key repeated more than once anywhere in the argument list (e.g. two `simulation=...` or two `num_threads=...`) is a usage error — reject it explicitly rather than silently letting the last (or first) occurrence win. This applies to every recognized key, including `num_threads=`; `-verbose` appearing more than once is harmless and need not be rejected.
- `num_threads=` is optional. If present, it must parse as an integer `>= 1`; `0`, negative values, and non-numeric values are all invalid and rejected with a usage error (they don't correspond to any case the assignment defines — the assignment only describes "missing", `=1`, and `>=2`). Missing or `=1` means single-threaded; `>=2` is a valid, accepted value. Store whatever valid value was parsed; do not act on it differently in this stage — every accepted value (missing, `1`, or `>=2`) still runs single-threaded, sequentially, here (see scope note above; actually using `>=2` to spawn worker threads is later work).
- Exact usage text and error-message wording are explicitly the implementation's choice per the assignment — pick something clear and stay consistent between the two modes.

**Verify:** run `simulator_322889890_315113738` (once Stage 4 wires `main`, or via a temporary throwaway `main()` linking only `CliOptions.cpp` for this stage).

Comparative mode: no args; `-comparative` with each mandatory key missing one at a time; a `simulation=` pointing at a nonexistent file; a `mission_control_folder=` pointing at an empty directory; a `mission_control_folder=` containing exactly one real `.so`; an unsupported `foo=bar` key; a valid invocation with `-comparative` placed *last* instead of first (e.g. `simulation=... mission_control_folder=... algorithm=... -comparative`); `num_threads=2` (must be accepted); `num_threads=0`, `num_threads=-1`, and `num_threads=abc` (must all be rejected); a repeated key, e.g. two `simulation=...` occurrences (must be rejected); both `-comparative` and `-competition` present together (must be rejected). Confirm the valid cases (including the reordered one and `num_threads=2`) populate `ComparativeOptions` correctly.

Competition mode, symmetrically: a fully valid `-competition` invocation (`simulation=`, `mission_control=`, `algorithms_folder=`) populates `CompetitionOptions` correctly; `-competition` with each mandatory key missing one at a time; an `algorithms_folder=` pointing at an empty directory; an `algorithms_folder=` containing exactly one real `.so`; a repeated key (e.g. two `mission_control=...`) rejected; and — the mode-specific case — a `-competition` invocation supplying `mission_control_folder=`/`algorithm=` (the comparative-only keys) instead of, or alongside, `mission_control=`/`algorithms_folder=`, which must be rejected as unsupported for `-competition` even though those exact keys would be valid under `-comparative`.

Every rejection case above must print a usage message identifying the specific problem and must not proceed further.

## Stage 3 — Comparative / competition orchestration

**New files:** `Simulator/include/Simulator/SimulatorRunner.h`, `Simulator/src/SimulatorRunner.cpp`, `Simulator/include/Simulator/CerrContextGuard.h`, `Simulator/src/CerrContextGuard.cpp` (see below).

**Narrowly touched (one behavior-preserving edit only):** `Simulator/src/SimulationManager.cpp` — remove its local `PrefixingStreambuf`/`CerrContextGuard` definitions and `#include <Simulator/CerrContextGuard.h>` instead; `runInternal`'s existing `CerrContextGuard cerr_guard(contextLabel(...))` call site is otherwise unchanged.

**Shape:**
```cpp
namespace simulator {

// Parses `options.simulation_composition_file` once, loads `options.algorithm_so_file` once,
// then for every entry in `options.mission_control_libraries`: attempts to load it; on failure
// records its full filename (with .so) into the errors list and moves on; on success runs the full
// composition through a fresh SimulationRunFactoryImpl + SimulationManager pair, writes that
// component's own `writeSimulationOutput(...)` YAML as a flat file directly under `results_dir`,
// and accumulates its `computeComponentTotals(...)`. Finally writes the top-level report via
// `writeComparativeReport(...)` into `results_dir`. Returns the count of components that ran (for
// the "ran N run(s)" summary line).
std::size_t runComparative(const ComparativeOptions& options, const std::filesystem::path& results_dir);

// Symmetric: loads `options.mission_control_so_file` once, loops `options.algorithm_libraries`,
// writes per-component YAML + `writeCompetitiveReport(...)`.
std::size_t runCompetition(const CompetitionOptions& options, const std::filesystem::path& results_dir);

} // namespace simulator
```

**Required decisions:**
- Parse the composition file exactly once per call (`ConfigLoader::parseCompositionData`) and reuse the same `ParsedComposition` for every component — do not reparse per component.
- Sort `options.mission_control_libraries` / `options.algorithm_libraries` by filename (e.g. `std::sort` comparing `path.filename().string()`) before the per-component loop. Stage 2's folder scan yields entries in whatever order the OS's `directory_iterator` produces, which is not guaranteed alphabetical or stable across platforms or runs; sorting first makes component processing order — and therefore `results_summary`/`errors` ordering in the top-level YAML, and this stage's own tests — deterministic and reproducible.
- Two distinct name forms per component `.so` path — do not conflate them:
  - `component_name = path.filename().string()` (**with** `.so`, e.g. `"MissionControl_111_222.so"`) — used for every identifier that ends up *inside* the YAML content: `computeComponentTotals(component_name, report)`'s `name` argument, and the failures list entry. Every example in the assignment (`same_results: ["manager1.so", ...]`, `errors: ["manager7.so", ...]`, `algorithm: "algorithm1.so"`) shows the full filename with extension, never a bare stem — match that exactly.
  - `component_stem = path.stem().string()` (**without** `.so`) — used only for filesystem naming: the per-component map-output subdirectory and the per-component detailed-YAML filename (see below). This half is explicitly "your decision" per the assignment, unlike the YAML content identifiers above.
- The **fixed** component for this invocation — `options.algorithm_so_file` in comparative mode, `options.mission_control_so_file` in competition mode — is loaded once, before the per-component loop. Its `Registrar::loadMappingAlgorithm`/`loadMissionControl` call is **not** wrapped in a try/catch here: let a throw propagate straight out of `runComparative`/`runCompetition` to Stage 4's existing top-level `try/catch` around that call. Do not record it as a failed "component", and do not write `comparative_report.yaml`/`competitive_report.yaml` or any per-component YAML in that case. This is deliberate: every loop entry depends on this one factory, so its failure means nothing meaningful can run at all — neither YAML schema in the assignment has an `errors:`-list slot for it (both examples only ever list loop entries there), and reporting "0 components ran" as a normal, if empty, result would misrepresent a total failure as a partial one. Stage 4's top-level catch already logs the message into `error.log` (redirection is already active by then) and exits non-zero; no new logging mechanism is needed for this case.
- Inside the loop, each remaining `.so` gets **two** separate try/catch blocks, both with the same *outcome* (log immediately, record `component_name` in the failures list, `continue` to the next library) but different *causes*, so the log records which phase failed:
  1. **Load phase:** `Registrar::loadMappingAlgorithm`/`loadMissionControl` for *that loop entry's* `.so` only. Catch `simulator::SimulationException` (and, defensively, `std::exception`); message e.g. `"failed to load " + component_name + ": " + e.what()`.
  2. **Run/write phase:** everything from constructing `SimulationRunFactoryImpl` through `manager.run(...)`, `writeSimulationOutput(...)`, and `computeComponentTotals(...)` for that component, in one try/catch around the whole block. `SimulationManager::run()` already catches ordinary per-run failures internally (scoring them `-1` inside that component's own detailed YAML, per the confirmed forum clarification — never surfacing in the top-level `errors:` list), so it does not normally throw for that reason — but it is not exception-free: `std::filesystem::create_directories(leaf_dir)` inside `SimulationManager::runInternal` is called without an `error_code` and can throw `std::filesystem::filesystem_error` (permissions, disk full, ...), and a failure to open/write this component's own output YAML would likewise throw. Treat any such throw here as "this component could not be run at all" (matches the confirmed forum wording exactly); message e.g. `"component " + component_name + " failed during simulation/output: " + e.what()`.
  Both catches happen inside the component-prefix guard below, so both land in `error.log` correctly attributed; neither relies on the final `errors:` YAML list alone, which only records *which* components failed, never *why* — the log must capture the reason the moment it's known, not deferred (Assignment 2's error-logging rule). Do not let one bad `.so`, in either phase, abort the run of the rest.
- Extract `PrefixingStreambuf` and `CerrContextGuard` out of `Simulator/src/SimulationManager.cpp`'s anonymous namespace into `Simulator/include/Simulator/CerrContextGuard.h` + `Simulator/src/CerrContextGuard.cpp` (namespace `simulator`, no longer anonymous) — verbatim, no behavior change, pure relocation — and update `SimulationManager.cpp` to `#include` it instead. Carry the existing `// TODO(A3 multithreading): review this global std::cerr redirection before running multiple SimulationManager instances concurrently.` comment onto the new header, extended to note that this stage's own use (below) inherits the same limitation. Do this instead of writing a second, independent copy of the same class in `SimulatorRunner.cpp`: `std::cerr::rdbuf()` is one process-wide mutable pointer with no synchronization, so two threads each redirecting it independently will race and can corrupt or misattribute output — this mechanism is *correct only* because both `SimulationManager` today and this stage's use of it execute strictly sequentially, and the codebase already flags it as needing rework once execution is concurrent. Duplicating the class now would mean fixing that same known limitation in two places later instead of one. Do not attempt to make it thread-safe now — that redesign is out of scope for this plan.
- In `SimulatorRunner.cpp`, wrap each loop entry's whole two-phase attempt (load try/catch **and** run/write try/catch above) in one `simulator::CerrContextGuard` constructed with `"component=" + component_name`. `SimulationManager` already applies its own inner `[sim=... mission=... drone=... lidar=...]` prefix per run via the same (now-shared) class; the two nest correctly (outer component prefix, inner per-run prefix), so every line in the single combined `error.log` (Stage 4) stays attributable to both its component and its specific run.
- Per component, inside the run/write-phase try block: `auto factory_impl = std::make_unique<SimulationRunFactoryImpl>(mapping_algorithm_factory, mission_control_factory, options.verbose); SimulationManager manager{std::move(factory_impl)};` then `manager.run(parsed.composition, component_map_dir, parsed.file_paths)`. `component_map_dir = results_dir / component_stem` — `SimulationManager` itself creates the nested `simulations/<sim>/<mission>/<drone>__<lidar>/` structure underneath for the output map files; do not build that nesting here.
- Per component, call `writeSimulationOutput(report, parsed.file_paths, results_dir / ("simulation_output_" + component_stem + ".yaml"))` — as a **flat file directly under `results_dir`**, a sibling of the top-level `comparative_report.yaml`/`competitive_report.yaml`, not nested inside `component_map_dir`. The assignment's "In addition to the above [i.e. in addition to what the results folder already contains: map files, error logs, the one top-level report], all runs... will generate their own [YAML]... Files will be added to the same output folder" reads as a continuation of "the results folder should contain" — i.e. the *same single results folder*, not a per-component subfolder; the filename-embedded component name (`simulation_output_<stem>.yaml`) is what keeps these files from colliding with each other in that flat folder. Then call `computeComponentTotals(component_name, report)` and collect the totals into the vector passed to `writeComparativeReport`/`writeCompetitiveReport` at the end.
- Which side is "fixed" vs. "loop" (see above) is mode-dependent: comparative mode's fixed component is `options.algorithm_so_file` (via `loadMappingAlgorithm`) and its loop is `options.mission_control_libraries` (via `loadMissionControl` per entry); competition mode's fixed component is `options.mission_control_so_file` (via `loadMissionControl`) and its loop is `options.algorithm_libraries` (via `loadMappingAlgorithm` per entry). The fixed component's one factory is reused for every loop entry.
- Do not call `dlclose` anywhere in this file — `Registrar` owns that (process teardown).

**CMake (verification target):** whatever target exercises `runComparative`/`runCompetition` for this stage's verification below — a temporary throwaway harness, or an extension of `simulator_registration_test`, or `simulator_322889890_315113738` once Stage 4 wires `main` — must list `src/CerrContextGuard.cpp` among its sources whenever it also compiles `SimulatorRunner.cpp` and/or `SimulationManager.cpp`: after this stage's extraction, neither `PrefixingStreambuf` nor `CerrContextGuard` is defined locally anymore, so any target linking either of those two `.cpp` files without also linking `CerrContextGuard.cpp` fails to link (undefined reference to the guard's constructor/destructor).

## Stage 4 — `main()` wiring and end-to-end run

**Change:** `Simulator/src/drone_mapper_simulation_main.cpp` (full rewrite, same filename — do not rename the file or the executable target). Update `Simulator/CMakeLists.txt`'s `add_executable(simulator_322889890_315113738 ...)` source list to add `src/CliOptions.cpp`, `src/SimulatorRunner.cpp`, and `src/CerrContextGuard.cpp` (the other files it lists, including `src/SimulationManager.cpp`, are already correct). `CerrContextGuard.cpp` is required here for the same reason as Stage 3's verification target: this executable already compiles both `SimulationManager.cpp` (which now `#include`s the shared header instead of defining the classes locally) and `SimulatorRunner.cpp` (which uses them directly), so omitting it is a link failure, not just a missing feature.

**Logic:**

   Then, still before any try/catch exists in `main`, resolve collisions and create the directory using only the `error_code` overload of `create_directories` — do not pre-check with `exists()` at all, and rely solely on `create_directories`'s own return value to decide ownership:
   ```cpp
   std::error_code ec;
   std::filesystem::path results_dir = base_results_dir;
   for (int suffix = 2;; ++suffix) {
       const bool created = std::filesystem::create_directories(results_dir, ec);
       if (ec) {
           // A genuine filesystem error (permissions, disk full, ...) -- not "name taken".
           std::cerr << "..."; return 1;
       }
       if (created) {
           break; // ec clear and `created` true: this call itself made the directory. Ours.
       }
       // ec clear but `created` false: the path already existed. Either it was a normal
       // collision, or another invocation's create_directories() won a race against this
       // one for this exact candidate name in between our attempts -- either way, this
       // directory is not ours to use; do not treat "already existed" as success. Try
       // the next suffix instead of proceeding with it.
       results_dir = base_results_dir;
       results_dir += "_" + std::to_string(suffix);
   }
   ```
   A separate `exists()` pre-check would only reopen the exact race it's meant to guard against — a name confirmed absent by `exists()` can still be created by another process before this invocation's own `create_directories()` call runs, and `create_directories()` reports that case as `ec` clear, return value `false` (the same shape as an ordinary pre-existing collision), never as an error — so a check that only inspects `ec` after `create_directories()` (without also checking its boolean return) would silently accept and reuse a directory this invocation did not itself create, contradicting "never reuse or overwrite an existing directory." Checking `created` closes that window: this loop only ever exits with a directory this specific call actually made. Using the `error_code` overload throughout (never the throwing one) mirrors the style already used elsewhere in this codebase (`Registrar::LibraryHandle`, `CliOptions.cpp`'s folder validation) specifically so an ordinary filesystem failure here cannot crash the program via an uncaught `std::filesystem::filesystem_error`.
